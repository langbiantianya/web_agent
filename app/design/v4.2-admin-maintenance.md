# V4.2：后台治理与运行期维护

> V4.2 不改变 Agent、Workflow、MCP 或 Skill 的外部协议，重点补齐管理后台、长期运行资源回收
> 与测试稳定性。版本目标是把“能配置”推进到“能运营、能观察、能自愈”。

## 1. 目标与边界

本版本处理四类运行期问题：

1. MCP stdio/远端连接在空闲后应及时释放，避免子进程和网络会话长期驻留。
2. checkpoint 在进程崩溃、删除失败或数据库记录丢失后会留下孤儿 thread，需要周期巡检兜底。
3. Skill 已有完整 API，但需要一个覆盖创建、编辑、导入、导出、资源、修订和 Agent 绑定的管理界面。
4. Windows 全量测试混跑真实 studio 子进程时，需要隔离 gRPC fork 状态污染。

本版本不包含 PostgreSQL、PgBouncer、MCP 多实例共享在线状态、审计账本或工具完整结果持久化；
这些事项继续由 [TODO](../../docs/design/TODO.md) 管理。

## 2. MCP 空闲连接回收

`McpClientManager` 启动周期巡检任务，按 `MCP_IDLE_SWEEP_INTERVAL_SEC` 调用 `close_idle()`。
默认回收阈值仍是 `MCP_IDLE_TIMEOUT_SEC`。

在途请求由 `McpConnection._inflight` 保护：

- 进入 `request()` 时计数加一，结束或取消时在 `finally` 中减一。
- 只有计数为零且超过空闲阈值的连接才会从管理器摘除并关闭。
- 应用关闭时 `mcp_manager.shutdown()` 先停止巡检，再关闭全部连接。

这样既不会因为一次长工具调用误判空闲，也不会让 stdio 子进程无限驻留。

## 3. checkpoint 孤儿治理

正常路径在 run 进入终态后立即删除 `run-<id>` checkpoint thread。V4.2 增加启动时清理与周期清理：

| 场景 | 动作 |
| --- | --- |
| run 已在数据库进入终态 | 立即删除对应 thread |
| thread 存在，但数据库已经没有对应 run | 超过保留期后删除 |
| thread 名不是 `run-<id>` | 不处理，避免误删其它消费者数据 |
| 扫描或单项删除失败 | 记录日志，等待下一周期 |

配置项：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `CHECKPOINT_CLEANUP_ENABLED` | `true` | 是否启用周期清理 |
| `CHECKPOINT_CLEANUP_INTERVAL_SEC` | `300` | 巡检间隔 |
| `CHECKPOINT_ORPHAN_RETENTION_SEC` | `86400` | 数据库无对应记录时的保留期 |
| `CHECKPOINT_CLEANUP_SCAN_LIMIT` | `1000` | 单次扫描上限，控制低内存机器开销 |

启动时先执行一次“遗留 running run 恢复”，再清理 checkpoint，确保崩溃后的 run 状态与暂停点
一致。清理失败不阻塞服务启动。

## 4. Skill 管理后台

`web/admin.html` 新增 Skill 管理页，直接使用既有 `/api/skills`：

- 新建、编辑、启停和删除 Skill。
- ZIP 导入与导出。
- 资源列表、文本/二进制上传和删除。
- 修订历史查看与回滚。
- 查看绑定当前 Skill 的 Agent。

Agent 编辑页增加启用 Skill 勾选绑定。绑定前展示 Skill 的 `allowed-tools` 与 Agent 工具白名单
差异；该提示只帮助运营发现配置不一致，**不会授予工具权限**。实际授权仍只以 `agent.tools`
为准。

### 4.1 运行档可视化

Skill 列表和详情返回 `runtime_profile`、`runtime_image`、`runtime_available` 与
`runtime_detail`：

- `fast` 在 studio 可用时可用。
- `isolated` 同时要求 studio 能力、版本、镜像目录和 profile 匹配。
- 未配置 studio 时返回不可用原因，不把不可用档位描述成可执行。

### 4.2 导入风险提示

导入完成后做静态扫描，并把结果写入 `import_warnings`。扫描不执行脚本，检查：

- Python 第三方 import。
- 常见网络访问痕迹，例如 `requests`、`httpx`、`curl`、`socket` 与 `fetch`。
- shebang 与脚本扩展名不一致。

风险提示用于人工复核；Skill 包结构、路径、大小与 zip slip 等硬性校验仍由导入服务执行。

## 5. isolated 延迟提示

`skill_exec` 的工具描述明确说明 isolated 会启动一次性 sandbox，可能额外耗时数秒；毫秒级纯
计算优先使用内置工具。该提示只影响模型选择，不改变白名单、档位解析或失败语义。

## 6. studio 启动与 dispatcher 就绪

Compose 的 `depends_on` 只保证容器启动顺序，不保证 dispatcher 已经监听端口。V4.2：

- 为 dispatcher 增加 HTTP `/health` 容器健康检查。
- studio 使用 `condition: service_healthy` 等待 dispatcher 就绪。
- studio 启动时仍在 `STUDIO_ISOLATED_STARTUP_BUDGET_MS` 内做退避重试，覆盖非 Compose
  部署、慢启动和临时连接失败。

预算耗尽后 studio 仍可提供 fast 档，但 isolated 会明确标记不可用，不会静默降级。

## 7. 测试与凭据

`tests/conftest.py` 在导入 `app.*` 前设置 `GRPC_ENABLE_FORK_SUPPORT=0`，覆盖 Windows 上
普通测试与 studio 子进程混跑时的 atfork 污染。

真实服务器验证使用临时环境变量注入数据库、Redis、studio 与 MiniMax 凭据。任何 API Key、
数据库密码和服务器密码都不写入 `.env`、测试快照、日志或 Git。

## 8. 验收

- MCP 空闲连接只回收无在途请求的连接，应用关闭后所有连接释放。
- 终态 run 和无主过期的 checkpoint thread 可被清理，未知 thread 不受影响。
- Skill 后台覆盖 CRUD、ZIP、资源、修订回滚和 Agent 绑定。
- isolated 不可用原因与 `allowed-tools` 差异在后台可见。
- dispatcher 慢启动时，studio 在预算内重试；Compose 健康检查阻止错误顺序启动。
- 全量本地测试与 MySQL/Redis 低资源服务器回归通过。
- `git diff --check`、docstring 与 proto 契约检查通过。

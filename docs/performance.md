# 性能与容量

> 本文是 web-agent 的**实测报告与容量推算**。
> 数据来自 `scripts/bench.py` 的真实压测，推算的每一条前提都写明了。
> 设计取舍见 [design.md](design.md)。

## 0. 先约定单位

全文用两个单位，别混：

- **事件（event）**：服务端 SSE 流里的一条 `token` 事件。压测脚本计的「token 数」
  就是它。假模型按 **2 个字符**切块（`tests/fake_llm.py` 的 `_split`），
  所以**一条 200 字的回复 = 100 个事件**。
- **字（≈ model token）**：模型吐出的字符数。中文分词器大约 **1 个 token 装
  1～1.5 个汉字**，下文推算一律用**字**做分母，结论里再折算回 model token。

**压测的回复长度固定 200 字**（= 100 个事件）。所有「每 token 成本」都是
**每 200 字回复**的成本。

## 1. 结论先说

**4c4g 单实例能撑多少并发，取决于三个东西，本服务只占其中最小的那一项。**

| 口径 | 4c4g 的数 | 依据 |
| --- | --- | --- |
| **CPU** | **约 2000–3750 字/s**（≈ 2000–3750 model token/s） | 实测服务端每字耗 0.8–1.5 ms CPU；4 核留 25% 给系统 ≈ 3 核 |
| **内存** | **约 9700 条并发流** | 实测基线 155 MB + 每条流约 0.3 MB（保守值）；4 GB 留 1 GB 给系统 |
| **SQLite** | **约 64 条并发流** | 实测：64 并发 0 失败，128 并发 28–30 个请求 500 |
| **模型配额** | 取决于供应商 | 一条流至少要一个模型请求；**这通常是真正的天花板** |

换算成「同时在线生成的用户数」（并发用户数 ≈ 字/s ÷ 每个用户的输出速率）：

| 每个用户的输出速率 | 4c4g 能同时服务的用户数（CPU 口径） |
| --- | --- |
| 20 字/s（慢模型 / 长输出） | **100–187 人** |
| 50 字/s（典型） | **40–75 人** |
| 100 字/s（快模型） | **20–37 人** |

上表按「1 model token = 1 字」折算。**中文分词器实际是 1 token ≈ 1～1.5 字**，
所以真实的 model token 口径要打个折：**50 model token/s 的用户 ≈ 50～75 字/s
→ 4c4g 约 30～45 人**。

**规划建议**：4c4g + MySQL，按 **30 个并发生成用户** 起步，按 **50 个** 做容量预案。
再往上就该加实例——本服务无状态，V2 的 Redis 架构支持多实例，扩容是线性的
（4 台 4c4g ≈ 120～200 人）。

**如果用 SQLite**：并发上限被钉在 **64**（§4.3）。生产必须用 MySQL。

## 2. 怎么测的

压测脚本：`scripts/bench.py`。

```powershell
# 饱和压测：假模型不 sleep，服务端成为瓶颈，量出「每字的 CPU 成本」
python scripts/bench.py --label saturated --chunk-delay 0

# 真实节奏：每 20ms 一个事件 ≈ 50 字/s/用户，接近真实模型
python scripts/bench.py --label realistic --chunk-delay 0.02
```

脚本做的事：

1. 建一个**独立的压测库**（临时目录，不碰开发库），跑 `alembic upgrade head`；
2. 起一个**真实的 uvicorn 子进程**（`python -m uvicorn app.main:app`），
   采集它的 **CPU 时间**与 **常驻内存**；
3. 起一个真实的 OpenAI 兼容假模型（`tests/fake_llm.py`）当模型后端；
4. 通过 HTTP 建 Agent / Workflow / 会话，然后按阶梯并发发消息、订阅 SSE，
   统计首字延迟、总延迟、事件数、字数；
5. 每档都**统计失败数**而不是整档中止——「64 并发挂了 2 个」本身就是结论。

采集进程指标**不依赖 psutil**：Windows 走 `GetProcessTimes` /
`GetProcessMemoryInfo`（ctypes），Linux 读 `/proc`。

> **一个 Windows 上的坑**：`.venv\Scripts\python.exe` 是个启动器 shim，
> `Popen().pid` 拿到的是它（3 MB），真正跑服务的是它的**子进程**（150 MB）。
> 脚本用 `CreateToolhelp32Snapshot` 往下找一层，量的是真身。

### 4.3 失败长什么样

128 并发时失败的请求全是同一个错误：

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
[SQL: INSERT INTO run (conversation_id, workflow_id, status, ...) VALUES (...) ]
```

原因在 §7.1：**SQLite 只有一个写者**，而 `POST /api/conversations/{id}/messages`
在同一个事务里先读后写。WAL 模式下这种「读事务升级为写事务」**不触发 busy
handler**——不等，直接失败。

**64 并发 0 失败，128 并发 28–30 个失败**：SQLite 的天花板在 64~128 之间。

## 5. 成本模型

从上面的数据里抽出三个可以外推的量。

### 5.1 每字的 CPU 成本

分母是**成功**的流数 × 200 字。失败的请求在 POST 阶段就挂了，一个字也没产出
（128 档饱和压测 30 个失败，分母从 25600 字降到 19600 字，差 23%）。

| 档位 | 饱和 | 真实节奏 |
| --- | ---: | ---: |
| 8 | 0.75 ms | 1.74 ms |
| 16 | 0.69 ms | 1.69 ms |
| 32 | 0.79 ms | 1.44 ms |
| 64 | 0.77 ms | 1.42 ms |
| 128 | 0.87 ms | 1.42 ms |

**区间 0.7–1.7 ms/字**。取三个值做规划：

| 口径 | ms/字 | 依据 |
| --- | ---: | --- |
| 乐观 | **0.8** | 饱和档稳态（32/64/128 档：0.79 / 0.77 / 0.87）——模型一口气吐完 |
| 中位 | **1.1** | 两个口径的中点 |
| 保守 | **1.5** | 真实节奏稳态（1.42～1.44）再留冷启动余量 |

**为什么真实节奏反而更贵？** 因为每条流的固定开销（订阅队列、心跳、SSE 帧、
连接）是按**流存活时间**摊的，不是按字摊的。同样吐 200 字，真实节奏下这条流
活了 2 秒多、饱和档只活了零点几秒——按时间计的开销摊到同样多的字上，每字自然
更贵。**生产里模型按 20～100 字/s 慢慢吐，接近真实档，所以按 1.4～1.5 ms 规划
更稳。**

> 注意这里的字/s **不是服务端的能力上限**：饱和压测里假模型和压测客户端
> 在同一个进程抢 CPU，1000 字/s 是**它们**的天花板，服务端只是全吞了。
> 能外推的是「每字耗多少 CPU」，不是「每秒能吐多少字」。

### 5.2 每条并发流的内存

用**每一档开始前后的 RSS 差**（`rss_delta_mb`）算——每档的基线就是上一档结束时
的服务端状态，差值才是这一档新开的流真正多占的内存。

| 档位 | RSS 增量 | 成功流数 | 每条流 |
| --- | ---: | ---: | ---: |
| 64（饱和） | 9.6 MB | 64 | 0.15 MB |
| 128（饱和） | 13.7 MB | 98 | 0.14 MB |
| 64（真实） | 7.6 MB | 62 | 0.12 MB |
| 128（真实） | 27.1 MB | 100 | 0.27 MB |

8 并发那两档算出 0.44～0.48 MB/条，明显偏高——那是连接池和线程池**首次扩容**
的一次性开销摊在了头几条流上，不是稳态成本。

**稳态约 0.12～0.15 MB/条，取保守值 0.3 MB/条**做推算。

**它随回复长度线性增长**：订阅队列是**无界**的（`app/core/bus.py` 里有意为之——
生成侧绝不能被读得慢的连接拖住），慢客户端的连接活多久，队列就堆多久。
2000 字的回复，每条流约 3 MB。

### 5.3 基线占用

**155 MB**（Python + FastAPI + LangGraph + SQLAlchemy + 连接池 + 缓冲）。

### 5.4 服务端不是 CPU 密集型

即使 64 条并发流，服务端也只用了**不到 1 核**（76–87% 核）。
它是个 IO 密集型服务：绝大部分时间在等模型。

## 6. 4c4g 推算

### 6.1 CPU 口径

```
可用核数   = 4 × 0.75            = 3 核（留 25% 给 OS、框架、GC）
字/s      = 3 ÷ 每字的 CPU
           = 3 ÷ 0.0008 ~ 0.0015 = 2000 ~ 3750 字/s
并发用户数 = 字/s ÷ 每个用户的输出速率
```

| 每用户输出速率 | 保守（1.5 ms/字） | 中位（1.1 ms/字） | 乐观（0.8 ms/字） |
| --- | ---: | ---: | ---: |
| 20 字/s | 100 人 | 136 人 | 187 人 |
| 50 字/s | 40 人 | 54 人 | 75 人 |
| 100 字/s | 20 人 | 27 人 | 37 人 |

**再折回 model token**：中文 1 token ≈ 1～1.5 字，50 model token/s 的用户实际
吃 50～75 字/s → 保守口径下是 **30～40 人**。这是 §1 规划建议的由来。

### 6.2 内存口径

```
可用内存 = 4096 − 155（基线）− 1024（OS / 文件缓存 / 安全余量）= 2917 MB
并发流数 = 2917 ÷ 0.3 MB = 约 9700 条（200 字的回复）
          2917 ÷ 3.0 MB = 约 970 条（2000 字的回复）
```

**内存比 CPU 宽一个数量级**，不是瓶颈。

### 6.3 SQLite 口径

**约 64 条**（实测：64 并发 0 失败，128 并发 28–30 个失败）。

### 6.4 取小者

| 部署形态 | 4c4g 的实际上限 |
| --- | --- |
| 4c4g + **MySQL** | **CPU 口径：40–75 人**（每用户 50 字/s，中位约 54）；折成 model token 口径 **30–45 人**。内存和 DB 都不是限制 |
| 4c4g + **SQLite** | **DB 口径：约 64 条流** |

**加上模型的并发配额**才是完整答案：

```
实际并发用户 = min(本服务能力, 模型供应商配额)
```

模型配额不够时，加机器**没用**——每条流都要模型给一个响应。

## 7. 压测暴露的问题（已修）

### 7.1 SQLite 并发写直接报错

**现象**：并发 128 时约 23% 的请求 500（`database is locked`）。

**根因**：SQLite 默认日志模式是 `delete`（回滚日志），写事务对整个库加**排他锁**；
默认 `busy_timeout` 只有 5 秒。而且 WAL 模式下「读事务升级为写事务」**不触发
busy handler**——不等，直接失败。

**修法**（`app/config/db.py`）：

- `journal_mode=WAL`：写者与读者不再互斥。**每进程只切一次**——切它要拿库的
  排他锁，每条连接都切会撞上别的连接持有的读事务，把测试套件偶发挂住（实测踩到）。
- `busy_timeout=15000`：撞上写者时排队等，而不是立刻失败。
- `synchronous=NORMAL`：WAL 下的推荐档位。

**试过但放弃**：`BEGIN IMMEDIATE`（SQLAlchemy 官方并发写配方）能让「先读后写」
不再撞锁，但它让**每个**事务一上来就握写锁，任何「跨 await 持有事务」的地方
都会把别人堵死——SSE 流整个生命周期都占着一个请求级事务，一开流别的写入就全挂。
**把报错变成死锁更糟**，所以保持 deferred，只靠 WAL + busy_timeout 缓解。

**结论**：SQLite 只适合开发与单机小流量，生产用 MySQL。

### 7.2 SSE 流一直占着 DB 连接（影响远大于 7.1）

**现象**：不是压测撞出来的，是顺着 7.1 查下去发现的。

**根因**：FastAPI 的 yield 依赖（`get_db`）是在**响应发完之后**才关闭的，
而 SSE 响应会一直开着。于是这个请求的 DB 事务跟着整条流一直挂着——
→**每条开着的 SSE 流都占住连接池里的一个连接**。

**影响（生产配置）**：MySQL 的默认池是 `pool_size=10` + `max_overflow=20`，
**最多 30 个连接**。也就是说：

> 不修的话，整个服务**最多 30 条并发 SSE 流**，第 31 个请求堵在等连接上。

4c4g 推算出的「几千条流」会直接掉到 30。**这才是并发上限的真正杀手**，
比 SQLite 那 64 还早撞上。

**修法**（`app/api/routes/run.py`）：路由把要的数据取完之后，**在返回流之前
就 `await db.rollback()`**——事务结束，连接立刻归还池子。

**回归测试**（`tests/test_db_concurrency.py`）：直接调路由，断言
`db.in_transaction()` 为假。去掉修复这条测试会失败（已验证）。

顺带的好处：SQLite 的 WAL 只能在没有活跃读快照时 checkpoint，流一直开着
WAL 文件就一直涨；回滚之后就能正常 checkpoint。

## 8. 已知偏差与局限

写下来是为了**别把这份报告当成绝对值**：

1. **压测客户端、假模型、服务端同机抢 4 核。** 实测的服务端 CPU 占用是下界；
   延迟数据被大幅放大（真实节奏下 32 并发 p95 首字 8.3 s，瓶颈在假模型
   不在服务端——服务端自己只用了 0.75 核）。**生产里模型在远端、服务端独占
   4 核，延迟会更好看，但本机测不出那个数。**
2. **只测了 MySQL 的替代路径。** 本机没有 MySQL 凭据，压测跑的是 SQLite。
   MySQL 的行级锁 + MVCC 不受本文的 pragma 影响，§6.1 / §6.2 的推算基于
   「DB 不是瓶颈」这个假设，**未在 MySQL 上实测**。
3. **只测了单节点工作流。** 真实的多节点 DAG 会多几次模型调用与事件，
   单字成本基本不变，但每 run 的固定开销会上升。
4. **内存按 200 字的回复估。** 回复越长，每条流占的内存越多（§5.2）。
5. **「1 model token = 1 字」是近似。** 中文分词器实际 1 token ≈ 1～1.5 字，
   折算后的用户数比 §6.1 的表低 20%～35%。
6. **Windows + 无 uvloop。** 事件循环每次调度的开销比 Linux + uvloop 高，
   逐字成本大概率偏乐观。生产部署在 Linux 上时，每字成本可能再低 10%～30%。
7. **没有测多实例。** Redis 模式下的跨实例事件转发会增加一点开销，
   但本服务无状态，量级不变。
8. **没有测真实模型的限流。** 而这恰恰是生产环境最先撞到的墙。
9. **Redis 在局域网另一台机器上（192.168.1.5）。** 网段抖动时整套 Redis 集成
   用例会变慢甚至失败。连接池已配 ``socket_timeout=5s``（见
   ``app/core/redis_client.py``），抖动时是「5 秒后明确报错」而不是「无限期
   挂死」——这条是踩过坑才加的：缺读超时时，一个抖动的读能把整条生成流程
   冻住，外部看是「服务没反应」，日志里却什么都查不到。
